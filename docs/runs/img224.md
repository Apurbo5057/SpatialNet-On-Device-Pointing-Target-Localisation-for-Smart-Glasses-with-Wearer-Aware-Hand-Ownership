# Run: 224 px input (`runs/img224/`)

## Setup

- **Kaggle kernel:** `spatialnet-train-224`, version 2. Version 1 failed only because Kaggle could not mount the dataset.
- **Same as the main run:** code, data, model, settings and seed 42.
- **Only change:** `--img_size 224` instead of 160.
- **Model:** 722,104 parameters, unchanged. The grid becomes 28×28 instead of 20×20, and compute 0.45 instead of 0.23 GFLOPs.
- **Input detail:** the stored dataset is 224×224, so this run sees the images at full stored resolution, while the main run sees them downsampled.

## Training health

- No errors in the log.
- Early stopping after 84 epochs; best checkpoint at epoch 59. The main run went to 125 epochs, best at 100.
- 1 h 16 min, 53 s per epoch.
- **It trained for fewer epochs than the main run.** Its learning rate was still near the peak, so the gains below come despite shorter training.

## Results against the main run

Paired on the same 2,604 test images; `*` marks a 95% bootstrap interval that excludes 0.

| Metric | 160 px | 224 px | Difference |
|---|---:|---:|---:|
| Target P@0.5 | 58.9 | **62.4** | +3.5 * |
| Target P@0.7 | 31.8 | **37.1** | +5.3 * |
| Target mIoU | 53.3 | **54.8** | +1.5 * |
| Target P@0.3 | 78.6 | 78.8 | +0.2 |
| On-object P@0.5 | 66.0 | 68.3 | +2.3 * |
| Near P@0.5 | 49.2 | 53.8 | +4.5 * |
| **Far P@0.5** | 25.4 | **35.9** | **+10.5 *** |

| Hand mIoU | 73.7 | 74.9 | +1.2 * |

## Where the gain comes from

- **Better boxes, not a better direction.** The direction error did not change significantly.
- **Extent.** When the predicted centre lies on the right object, P@0.5 rises from 69.4% to 74.5%. Extent failures drop from 199 to 171.
- **Fingertip.** About 25% more precise (2.43% → 1.81% of image width).
- **Medium and large targets gain most.** Targets covering 20–45% of the image: 64.8% → 71.4%.
- **Small targets do not gain at 224 px.** Targets under 3% of the image: 36.9% → 33.0% (not significant). They are still drawn too large: 1.9× before, 2.2× now.
  - **Correction after the 320 px run:** small targets do improve at 320 px (46.6%), where the images were re-converted with real extra detail. The 224 images carry no more detail than the 160 input needs, so the limit at 224 px was the data, not only the size head. See `img320.md`.
- **Wrong-object picks went up** (171 → 211), while extent and direction failures went down. The total number of failures is about the same (558 → 553).

## Cost

- Compute: 0.23 → 0.45 GFLOPs (2×).
- Latency in PyTorch, measured on the Kaggle machine:
  - CPU, 1 thread: 25.7 → 37.2 ms (+45%);
  - GPU (T4): 15.9 → 16.4 ms.
  - These numbers vary by about ±15% between runs on the same model (A1, identical to the main model, measured 29.0 ms), so treat them as rough.
- **The on-glasses latency still needs measuring (T2).**

## Verdict

- **Resolution was a real bottleneck, especially for far targets.** That is the weakest case and the one the paper's ray idea is about.
- **The parameter count is unchanged**, so the "0.72M parameters" claim still holds.
- **Caveat:** one seed. The paired intervals cover the variation across test images, not across training runs.
- **Next:** test whether a still larger input helps. The dataset was re-converted at 320 px because the stored images are only 224, and a 320 px run is next.
